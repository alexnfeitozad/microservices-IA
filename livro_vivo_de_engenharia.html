Sobre este livro

Este não é um livro para decorar tecnologias. É um livro para aprender a construir.

Através de um sistema real, cada decisão será analisada sob três perguntas fundamentais:

O QUE?
O que estamos construindo?
POR QUÊ?
Por que precisamos disso?
COMO?
Como isso é implementado?

O objetivo é desenvolver conhecimento fundacional em engenharia de software que sobreviva à troca de linguagem, framework ou ferramenta de IA.

Introdução

Este projeto nasceu de uma pergunta fundamental:

"Como aprender microsserviços de verdade, sem apenas copiar arquiteturas prontas ou depender da IA para escrever código?"

A resposta será encontrada através da construção.

O projeto utilizará o eShopOnContainers original como nosso primeiro laboratório. Importante: Não iremos alterar o código original apenas para simplificar o aprendizado.

  • Primeiro entenderemos como o sistema original funciona.
  • Depois analisaremos suas decisões arquiteturais.
  • Somente posteriormente discutiremos modernizações, alternativas e melhorias.

Como utilizar este livro

A pessoa que acompanha este projeto não deve apenas copiar código. Ela deve conseguir explicar o que está fazendo, por que está fazendo e como uma tecnologia diferente resolveria o mesmo problema.

O Método de Construção Reutilizável

Não ensinamos o leitor a decorar nomes de classes nem receitas pré-fabricadas. Ensinamos a pensar o ciclo de engenharia:

REQUISITO → ENTENDER → DECIDIR ONDE PERTENCE → MODELAR → IMPLEMENTAR → TESTAR → VALIDAR → INTEGRAR → PUBLICAR → EVOLUIR

Esse método é o mesmo se você estiver construindo uma loja, uma farmácia ou um hospital. O domínio muda, o processo de construção permanece:

Domínio de Exemplo Entidade Central Fronteira de Negócio Aplicação do Método
E-Commerce (Loja) Product (Produto) Catálogo de itens vendáveis Requisito → Domínio isolado → API de catálogo
Farmácia Medicine (Medicamento) Estoque e retenção de receita Requisito → Regras de dosagem → Validação
Hospital Patient (Paciente) Prontuário e internação Requisito → Histórico clínico → Auditoria
Financeiro / Banco Account (Conta) Saldos e lançamentos Requisito → Imutabilidade contábil → Consistência

1.1 Requisito

● Em andamento

Objetivo desta etapa

O QUE É?

O requisito é a declaração explícita do que o sistema precisa realizar para gerar valor. Em arquitetura de software, nunca começamos escolhendo tecnologias (como Docker, Kafka, EF Core ou banco de dados). Começamos entendendo o problema que precisa ser resolvido.

NO MICROSSERVIÇO CATALOG

No laboratório do nosso sistema de comércio eletrônico, o microsserviço Catalog atende a três requisitos fundamentais:

📋 Requisitos de Negócio do Catalog

1. Vitrine de Produtos: Exibir para os visitantes os produtos disponíveis, com foto, descrição, preço e especificação.
2. Classificação: Permitir busca por texto, filtro por Marca (Brand) e filtro por Categoria/Tipo (Type).
3. Gestão de Estoque no Catálogo: Permitir cadastro, atualização de preço e alteração de quantidade disponível para compra.

Princípio de Engenharia

O Requisito dita o Limite do Serviço
Regra: Se você não tem clareza sobre o requisito, qualquer decisão técnica subsequente será um tiro no escuro.
Reutilização: Em uma farmácia, o requisito é listar Medicamentos e dosagens. Em um hospital, listar Pacientes e leitos. O método de captura do requisito é o mesmo.

1.2 Contexto do microsserviço

● Em andamento

Objetivo desta etapa

Definir o Contexto Delimitado (Bounded Context) e estabelecer onde o serviço vive no ecossistema.

O QUE É?

Em Domain-Driven Design (DDD), um microsserviço não deve tentar abraçar o mundo. Ele opera dentro de uma fronteira semântica bem definida: o Bounded Context. Dentro dessa fronteira, termos e modelos têm um significado estrito e compartilhado por todos.

O CONTEXTO DO CATALOG

O Catalog é a autoridade central e exclusiva sobre as especificações de produtos comercializados pela plataforma:

  • Ele é quem sabe quais produtos existem, quanto custam como preço base, suas descrições e imagens.
  • Ele não conhece regras de promoção de checkout, taxas tributárias individuais ou se a entrega será feita por transportadora X ou Y.
  • Para o Catalog, um produto é uma especificação vendável; para o serviço de frete, o produto é apenas peso e volume cúbico.

1.3 Responsabilidades

● Em andamento

Objetivo desta etapa

Fixar as obrigações que este microsserviço deve cumprir com autonomia perante os demais componentes.

RESPONSABILIDADES CENTRAIS

Para manter o serviço desacoplado e autônomo, ele assume compromissos contratuais claros:

  • Integridade dos Dados: Garantir que nenhum produto seja salvo com preço negativo, sem nome ou sem tipo associado.
  • Leitura Eficiente: Responder com extrema rapidez consultas de catálogo e listagens paginadas (a maior parte do tráfego de um e-commerce é leitura).
  • Autonomia de Armazenamento: Possuir seu próprio banco de dados isolado, permitindo evoluções de esquema sem pedir licença a outros microsserviços.

1.6 Fluxos principais

○ Próximo

Objetivo desta etapa

Mapear o fluxo de dados em cada operação típica do serviço antes de desenhar endpoints.

FLUXOS MAPEADOS

  1. Fluxo de Consulta Paginada: Cliente envia página, tamanho, filtro de tipo e marca → API valida parâmetros → Consulta filtrada no banco → Retorna página com totalizadores.
  2. Fluxo de Detalhes do Produto: Cliente solicita produto por ID → Consulta direta em cache/banco → Retorna DTO do produto ou 404 Not Found.
  3. Fluxo de Cadastro / Alteração de Preço: Administrador envia comando → Validação na camada de Aplicação → Entidade aplica invariantes no Domínio → Persistência no Repositório → Publicação de evento de preço atualizado.

CAPÍTULO 2 • DOMÍNIO

2.1 Criando o projeto Domain

✓ Concluído

Etapa Concluída na Solução

Criação do projeto de Class Library para abrigar as entidades, regras de negócio e interfaces do microsserviço.

O QUE FIZEMOS?

Criamos o projeto Catalog.Domain.csproj utilizando .NET 10 puro, sem nenhuma dependência de pacotes externos, sem Entity Framework e sem ASP.NET Core.

Catalog.Domain/Catalog.Domain.csproj 
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>

Decisão Arquitetural

Domínio Puro e Agnóstico
Por quê? O núcleo de negócio não deve mudar quando trocamos o banco de dados de PostgreSQL para SQL Server ou de Entity Framework para Dapper.
Trade-off no eShop legado: No eShopOnContainers original, muitas vezes pastas de infraestrutura conviviam no mesmo projeto da API, facilitando vazamento de dependências. A separação física em Catalog.Domain elimina esse risco.

CAPÍTULO 5 • API

5.9 Health Check

✓ Concluído

Etapa Concluída na Solução

Configuração do endpoint de diagnóstico e saúde da aplicação.

O QUE FIZEMOS?

Em sistemas distribuídos e orquestrados (como Docker Compose e Kubernetes), é indispensável que cada serviço informe seu estado de saúde para roteadores e balanceadores de carga. Configuramos os Health Checks no Program.cs:

Catalog.API/Program.cs 
var builder = WebApplication.CreateBuilder(args);

// Adiciona serviço nativo de Health Checks
builder.Services.AddHealthChecks();

var app = builder.Build();

// Mapeia o endpoint de saúde
app.MapHealthChecks("/health");

app.MapGet("/", () => "Catalog API está online!");

app.Run();

Decisão Arquitetural

Separação de Banco de Dados por Serviço
Por quê? Garantir autonomia e limites de contexto rígidos.
Benefício: Um serviço não derruba o outro por lock no banco.
Trade-off: Complexidade transacional (necessidade de consistência eventual).
Implementação .NET: Múltiplos DbContexts separados.
Alternativa Java: Spring Data JPA com datasources distintos.
