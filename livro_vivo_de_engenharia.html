1.2 Contexto do microsserviço

● Em andamento

Objetivo desta etapa

Definir o Contexto Delimitado (Bounded Context) e estabelecer onde o serviço vive no ecossistema.

O QUE É?

Em Domain-Driven Design (DDD), um microsserviço não deve tentar abraçar o mundo. Ele opera dentro de uma fronteira semântica bem definida: o Bounded Context. Dentro dessa fronteira, termos e modelos têm um significado estrito e compartilhado por todos.

O CONTEXTO DO CATALOG

O Catalog é a autoridade central e exclusiva sobre as especificações de produtos comercializados pela plataforma:

  • Ele é quem sabe quais produtos existem, quanto custam como preço base, suas descrições e imagens.
  • Ele não conhece regras de promoção de checkout, taxas tributárias individuais ou se a entrega será feita por transportadora X ou Y.
  • Para o Catalog, um produto é uma especificação vendável; para o serviço de frete, o produto é apenas peso e volume cúbico.

2.2 Identificando as entidades

✓ Concluído

Etapa Concluída na Solução

Mapeamento dos conceitos centrais do Bounded Context do Catalog que possuem identidade própria, ciclo de vida e estado contínuo.

O QUE SÃO ENTIDADES NO DOMÍNIO?

No Domain-Driven Design (DDD), uma Entidade é um objeto que possui uma identidade única e contínua ao longo do tempo. Dois objetos com os mesmos valores de atributos continuam sendo instâncias diferentes se seus identificadores forem distintos. Por outro lado, mesmo que o preço, a descrição ou a imagem de um produto sejam alterados, ele continua sendo o mesmo produto perante o negócio.

ENTIDADES IDENTIFICADAS NO MICROSSERVIÇO CATALOG

  • Product (Item do Catálogo): A entidade central do nosso bounded context. Representa a unidade vendável exibida na vitrine com nome, preço, descrição, foto e associações de tipo e marca.
  • CatalogBrand (Marca / Fabricante): Entidade que agrupa itens por fabricante ou marca parceira.
  • CatalogType (Tipo / Categoria): Entidade que classifica itens por categoria de produto (ex: canecas, camisetas, pins).

Decisão Arquitetural

Identidade Única e Foco no Comportamento
Modelagem Pura: Antes de pensar em tabelas do PostgreSQL ou Entity Framework, modelamos as entidades como classes puras em C# que protegem suas próprias regras.
Identificador: Definimos o identificador de Product de forma explícita, garantindo unicidade no ecossistema distribuído.

CONCEITO APRENDIDO: O QUE É UMA ENTITY?

Uma Entity (Entidade) não é simplesmente uma classe com propriedades soltas. No Domain-Driven Design (DDD), uma entidade é definida por quatro pilares essenciais:

  • Identidade: Possui um identificador único (`Id`) que a distingue de qualquer outro objeto ao longo de todo o seu ciclo de vida.
  • Estado: O conjunto de dados que a entidade carrega em um determinado instante.
  • Comportamento: Métodos e operações que expressam as regras e transformações de negócio.
  • Encapsulamento: O próprio objeto é o guardião do seu estado interno, impedindo alterações diretas e descontroladas vindas de fora.

💡 O Papel da Identidade no Domínio

O Id representa a identidade da entidade. Observe o exemplo:

Brand                     Brand
Id = 1                    Id = 2
Name = Nike               Name = Nike

Esses dois registros representam entidades diferentes no domínio, mesmo possuindo exatamente o mesmo nome, porque suas identidades são distintas.

ENTIDADES CONSTRUÍDAS NO DOMÍNIO

2.3.1 Estrutura base da entidade

Todas as entidades são construídas em C# puro (.NET 10), sem herança forçada de bibliotecas externas, sem Entity Framework e sem acoplamento técnico.

2.3.2 Product (Item do Catálogo)

Representa o produto do catálogo e possui:

Product
├── Id (Identidade única)
├── Name
├── Description
├── Price
├── PictureFileName
├── CatalogTypeId   (Referência à entidade CatalogType)
└── CatalogBrandId  (Referência à entidade Brand)

Os campos CatalogTypeId e CatalogBrandId representam referências às entidades relacionadas no catálogo.

Catalog.Domain/Entities/Product.cs 
namespace Catalog.Domain.Entities
{
    public class Product
    {
        public Guid Id { get; private set; }
        public string Name { get; private set; } = string.Empty;
        public string Description { get; private set; } = string.Empty;
        public decimal Price { get; private set; }
        public string PictureFileName { get; private set; } = string.Empty;
        public int CatalogTypeId { get; private set; }
        public int CatalogBrandId { get; private set; }

        public Product(Guid id, string name, string description, decimal price, 
            string pictureFileName, int catalogTypeId, int catalogBrandId)
        {
            Id = id;
            Name = name;
            Description = description;
            Price = price;
            PictureFileName = pictureFileName;
            CatalogTypeId = catalogTypeId;
            CatalogBrandId = catalogBrandId;
        }
    }
}

2.3.4 CatalogType (Tipo / Categoria)

Representa o tipo ou categoria do produto no catálogo:

CatalogType
├── Id
└── Name

Decisão Técnica de Nomenclatura

Por que CatalogType em vez de Type?
Motivo: Type é uma palavra excessivamente genérica e causaria ambiguidade e conflito direto com o tipo nativo System.Type da plataforma .NET (C#).
Clareza: CatalogType expressa com precisão a categoria dentro do Bounded Context do catálogo.
Catalog.Domain/Entities/CatalogType.cs 
namespace Catalog.Domain.Entities
{
    public class CatalogType
    {
        public int Id { get; private set; }
        public string Name { get; private set; } = string.Empty;

        public CatalogType(int id, string name)
        {
            Id = id;
            Name = name;
        }
    }
}

2.3.5 IDENTIDADE DAS ENTIDADES

Cada entidade define sua estratégia de identidade. Product adota Guid como identificador global único, permitindo geração descentralizada, enquanto Brand e CatalogType utilizam identificadores numéricos sequenciais (int) por se tratarem de tabelas de domínio controladas.

2.3.6 ENCAPSULAMENTO

Comparamos duas abordagens de modelagem:

// ❌ MODELO ANÊMICO (Qualquer parte externa pode corromper os dados):
public string Name { get; set; }

// ✅ ENTIDADE RICA E ENCAPSULADA (Estado protegido):
public string Name { get; private set; }

O modificador private set impede que partes externas alterem diretamente as propriedades. A alteração deverá posteriormente passar por métodos de comportamento da própria entidade, como UpdateName(...) ou UpdateDetails(...).

2.3.7 CONSTRUTORES

As entidades possuem construtores explícitos responsáveis pela criação inicial do objeto, garantindo que nenhuma entidade nasça sem seus dados essenciais.

Nota do método: As regras detalhadas e profundas de validação de invariantes serão tratadas na etapa 2.4 Regras de negócio. Não antecipamos regras que ainda não foram estudadas e testadas.

2.3.8 ESTADO DA ENTIDADE

O estado é o conjunto de valores das propriedades em um determinado momento. Ao proteger o estado com private set e construtores consistentes, garantimos que a entidade mantém sua integridade durante toda a execução do microsserviço.

RELACIONAMENTOS IDENTIFICADOS

No domínio do Catalog, identificamos os seguintes relacionamentos conceituais:

Brand 1 ─────── N Product

CatalogType 1 ─ N Product

O Product já possui os campos CatalogBrandId e CatalogTypeId que materializam essas associações.

⚠️ Princípio Arquitetural: Não Antecipar Infraestrutura

Identificar Relações ≠ Configurar ORM
Atenção: Identificamos o relacionamento conceitual no domínio, mas NÃO devemos introduzir ainda EF Core, propriedades de navegação de entidades (ex: public Brand Brand { get; set; }), Repository ou banco de dados.
Momento Certo: Esses assuntos pertencem às camadas de Infraestrutura e Persistência e serão tratados quando forem estritamente necessários.

PRINCÍPIO ARQUITETURAL APRENDIDO

O processo de construção de um domínio não deve criar uma entidade isoladamente quando o próprio modelo já permite identificar um conjunto de entidades relacionadas.

Por isso refinamos nosso fluxo de "2.3 Criando uma Entity" para "2.3 Construindo as Entidades". O objetivo é construir o conjunto inicial necessário para representar o contexto antes de aprofundar suas regras de validação.

        public int Id { get; private set; }
        public string Name { get; private set; } = string.Empty;

        public Brand(string name)
        {
            ValidateName(name);
            Name = name;
        }

        public void UpdateName(string name)
        {
            ValidateName(name);
            Name = name;
        }

        private static void ValidateName(string name)
        {
            if (string.IsNullOrWhiteSpace(name))
            {
                throw new ArgumentException("Brand name cannot be empty.");
            }
        }
    }
}

A validação garante que o nome da marca não seja nulo, vazio ou composto exclusivamente por espaços em branco, centralizada no método private static void ValidateName(string name).

🛡️ O Conceito Principal: A Auto-Proteção do Estado

"Uma entidade deve proteger seu próprio estado."

O modificador private set combinado com métodos explícitos de alteração permite que a entidade controle como seu estado pode ser modificado por chamadas externas:

Chamada Externa → UpdateName(...) → ValidateName(...) → Estado Válido

⚠️ IMPORTANTE: DUAS VALIDAÇÕES TOTALMENTE DIFERENTES

É fundamental que o engenheiro de software compreenda a fronteira entre regras locais e regras que dependem do ecossistema:

Fronteiras de Validação

Validação de Domínio vs. Validação de Persistência
1. Regra Local do Valor: CatalogBrandId > 0. É uma regra relacionada ao valor recebido (invariante local). A própria entidade Product valida isso imediatamente em memória.
2. Validação Externa / Existência: "A Brand realmente existe?". Isso exige consultar uma fonte externa/persistência de dados.
Regra de Ouro: NÃO coloque acesso ao banco de dados dentro da entidade de domínio puro. Esse assunto será tratado posteriormente quando chegarmos às camadas de infraestrutura e aplicação.

Decisão Arquitetural (ADR)

Por que não criar um NameValidator compartilhado agora?
Decisão: Encontramos validações semelhantes em Product, Brand e CatalogType, mas decidimos NÃO criar imediatamente um NameValidator compartilhado.
Motivos:
  • As regras podem evoluir de forma diferente para cada entidade no futuro.
  • Abstrair somente para eliminar poucas linhas duplicadas pode gerar acoplamento desnecessário.
  • Evita a armadilha de criar abstrações prematuras.
Lição: "Nem toda duplicação precisa imediatamente virar uma abstração."

CONCEITO APRENDIDO

Um Value Object é um objeto definido pelo seu valor (e não por um Id) e utilizado quando um conceito do domínio possui significado e/ou comportamento próprio que justifica seu encapsulamento.

Dois Value Objects com os mesmos valores são considerados idênticos e intercambiáveis (ex: duas notas de R$ 100 têm o mesmo valor).

💡 Ponto Principal Aprendido

"Não devemos criar Value Objects apenas porque estamos utilizando DDD."

A decisão correta depende da necessidade real do domínio.

Hoje:

Abordagem Vantagens (Pros) Trade-offs / Considerações
Relacionamento por ID (Adotada) • Mantém o Domínio 100% puro e sem dependência de ORMs.

Contexto: Em microsserviços onde entidades formam um Agregado coeso e inseparável (como um Pedido e seus Itens de Pedido), o uso de propriedades de navegação na raiz do agregado é natural. ESTRUTURA DO PROJETO DE TESTES

Para garantir que o domínio puro opere exatamente conforme as regras de negócio especificadas e protegido contra regressões, criamos o projeto de testes unitários:

  • Catalog.UnitTests (projeto de testes em .NET 10 com xUnit)

O projeto de testes referencia diretamente o domínio:

Catalog.UnitTests
       ↓ (referência de projeto)
Catalog.Domain

A direção da dependência é estritamente unidirecional: os testes dependem do domínio, mas o domínio não possui nenhuma dependência dos testes, preservando seu isolamento e pureza.

ESTRATÉGIA DE TESTES & PADRÃO AAA

Os testes unitários foram estruturados para verificar comportamentos e invariantes das entidades, e não simplesmente linhas de código para bater metas cegas de cobertura métrica.

Adotamos o padrão clássico AAA (Arrange, Act, Assert) em todos os cenários de teste:

1. Arrange

Preparar o cenário: instanciar dados válidos ou parâmetros limites para o teste.

2. Act

Executar o comportamento: invocar o construtor ou o método de alteração da entidade.

3. Assert

Verificar o resultado: assegurar o estado consistente ou a exceção esperada.

COMPORTAMENTOS TESTADOS NO DOMÍNIO

A suíte de testes unitários cobre integralmente as invariantes de cada entidade:

1. Testes da Entidade Product (Catalog.UnitTests/Entities/ProductTests.cs)

  • Criação com dados válidos: instanciação com todos os dados obrigatórios e verificação da atribuição de identidade e estado.
  • Rejeição de preço negativo: o construtor lança exceção ao receber preço menor que zero.
  • Atualização de preço: alteração segura através de método de domínio refletindo o novo valor no estado.
  • Rejeição de preço negativo durante atualização: tentativa de alteração para valor negativo lança exceção imediatamente.
  • Preservação do estado anterior: quando uma atualização inválida é rejeitada, o estado anterior da entidade permanece 100% íntegro e inalterado.
Exemplo de Teste no Padrão AAA (ProductTests.cs) 
[Fact]
public void UpdatePrice_WithNegativePrice_ThrowsArgumentOutOfRangeException()
{
    // Arrange: cenário com produto válido
    var product = new Product(Guid.NewGuid(), "Running Shoes", "Desc", 199.90m, "shoes.png", 1, 2);

    // Act & Assert: execução e verificação da exceção esperada
    var exception = Assert.Throws<ArgumentOutOfRangeException>(() =>
        product.UpdatePrice(-50m));

    Assert.Equal("price", exception.ParamName);
    Assert.Equal(199.90m, product.Price); // Estado anterior preservado
}

2. Testes da Entidade Brand (BrandTests.cs)

  • Criação válida: instanciação correta com identificador positivo e nome.
  • Rejeição de nome vazio: nomes nulos, vazios ou apenas com espaços em branco lançam ArgumentException.
  • Atualização do nome: alteração protegida que valida o novo nome antes de persistir no estado.

3. Testes da Entidade CatalogType (CatalogTypeTests.cs)

  • Criação válida: instanciação com Id e Name consistentes.
  • Rejeição de nome vazio: proteção contra strings vazias ou nulas.
  • Atualização do nome: validação completa ao executar UpdateName(...).

💡 Regra de Ouro sobre Testes de Domínio

"Testes devem proteger comportamentos relevantes do domínio. Não existe necessidade de criar um teste para cada linha de código."

Testar getters triviais sem lógica não agrega valor de engenharia. O valor real do teste unitário está em blindar as regras de negócio, as invariantes e os fluxos de erro.

🎓 Princípio de Aprendizado Reutilizável

Não memorizamos testes específicos de Product. O mecanismo reutilizável é:

Regra de Negócio → Comportamento Esperado → Cenário → Teste → Execução → Assert

Esse processo poderá ser aplicado posteriormente a qualquer domínio, como Medicine, Patient, Order, Invoice, Account etc.

🏛️ Fechamento do Capítulo 2: A Fundação do Domínio Concluída

O domínio do microsserviço Catalog agora possui uma base sólida e completa:

  • Entidades Ricas: Product, Brand e CatalogType em C# puro (.NET 10).
  • Regras de Negócio: Invariantes protegidas em construtores e métodos com private set.
  • Decisões sobre Tipos: Primitivos conscientes sem Value Objects artificiais ou prematuros.
  • Relacionamentos: Modelados explicitamente por identificadores sem acoplamento a ORMs.
  • Abstrações: Sem abstrações dogmáticas ou burocráticas no domínio.
  • Testes Automatizados: Suíte de testes unitários protegendo 100% dos comportamentos de negócio.

O objetivo não é memorizar Product, Brand ou CatalogType, mas aprender o processo de transformar requisitos em entidades, regras e testes.

5.9 Health Check

✓ Concluído

Etapa Concluída na Solução

Configuração do endpoint de diagnóstico e saúde da aplicação.

O QUE FIZEMOS?

Em sistemas distribuídos e orquestrados (como Docker Compose e Kubernetes), é indispensável que cada serviço informe seu estado de saúde para roteadores e balanceadores de carga. Configuramos os Health Checks no Program.cs:

Catalog.API/Program.cs 
var builder = WebApplication.CreateBuilder(args);

// Adiciona serviço nativo de Health Checks
builder.Services.AddHealthChecks();

var app = builder.Build();

// Mapeia o endpoint de saúde
app.MapHealthChecks("/health");

app.MapGet("/", () => "Catalog API está online!");

app.Run();

Decisão Arquitetural

Separação de Banco de Dados por Serviço
Por quê? Garantir autonomia e limites de contexto rígidos.
Benefício: Um serviço não derruba o outro por lock no banco.
Trade-off: Complexidade transacional (necessidade de consistência eventual).
Implementação .NET: Múltiplos DbContexts separados.
Alternativa Java: Spring Data JPA com datasources distintos.
